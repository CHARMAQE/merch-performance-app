\chapter*{R\'esum\'e}
\addcontentsline{toc}{chapter}{R\'esum\'e}
Ce rapport pr\'esente les travaux r\'ealis\'es dans le cadre d'un stage effectu\'e au sein de Smollan, pour le client Unilever, du 20 f\'evrier 2026 au 20 ao\^ut 2026. Le projet consiste \`a mettre en place une plateforme de suivi, de validation et d'analyse de la performance merchandising.

La solution s'appuie sur plusieurs composantes compl\'ementaires : une base de donn\'ees MySQL construite \`a partir de fichiers Excel extraits du portail, des traitements de transformation et de chargement des donn\'ees, des r\`egles de validation permettant de d\'etecter les anomalies, une application web destin\'ee au contr\^ole et \`a la validation des donn\'ees, une application mobile orient\'ee supervision terrain, ainsi qu'une couche Business Intelligence r\'ealis\'ee avec Power BI.

L'objectif principal est de remplacer progressivement le suivi quotidien manuel par une solution centralis\'ee, fiable et exploitable par les superviseurs et les \'equipes backend afin de contr\^oler l'ex\'ecution merchandising et de faciliter la prise de d\'ecision.

\textbf{Mots-cl\'es :} merchandising, performance, application mobile, tableau de bord, data engineering, Business Intelligence.

\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
This report presents the work carried out during an internship at Smollan, for the client Unilever, from February 20, 2026 to August 20, 2026. The project focuses on building a platform for merchandising performance monitoring, data validation, anomaly detection, and reporting.

The solution combines several components: a MySQL database built from Excel files extracted from the portal, data transformation and loading processes, validation rules for detecting anomalies, a web application for data control and validation, a mobile application for field supervision, and a Business Intelligence layer developed with Power BI.

The main objective is to gradually replace the manual daily reporting process with a centralized and reliable solution that helps supervisors and backend teams monitor merchandising execution and support decision-making.

\textbf{Keywords:} merchandising, performance, mobile application, dashboard, data engineering, Business Intelligence.

\chapter{Introduction g\'en\'erale}

\section{Contexte du stage}
Le stage s'inscrit dans le cadre de la formation Master Big Data et Internet des Objets. Il a \'et\'e effectu\'e au sein de Smollan, entreprise intervenant dans le domaine de l'ex\'ecution commerciale et du merchandising, pour le compte du client Unilever.

Le merchandising joue un r\^ole essentiel dans la disponibilit\'e, la visibilit\'e et la performance commerciale des produits en points de vente. Les \'equipes terrain assurent le suivi de l'ex\'ecution merchandising, tandis que les superviseurs ont besoin d'une vision claire sur l'\'etat des magasins, les anomalies d\'etect\'ees et les indicateurs de performance.

Avant la mise en place du projet, une partie du suivi reposait sur des rapports quotidiens transmis manuellement. Cette organisation peut limiter la rapidit\'e de contr\^ole, rendre l'analyse plus difficile et augmenter le risque d'erreurs ou d'informations dispers\'ees.

\section{Probl\'ematique}
Les processus de suivi merchandising deviennent difficiles \`a piloter lorsqu'ils reposent sur des fichiers dispers\'es, des rapports manuels et une validation non automatis\'ee des donn\'ees. Les fichiers Excel extraits du portail contiennent des informations importantes, mais ils n\'ecessitent une structuration, un chargement en base de donn\'ees et des r\`egles de contr\^ole pour devenir exploitables.

La probl\'ematique principale du projet est donc la suivante :

\textit{Comment concevoir une plateforme capable de transformer les donn\'ees extraites du portail en informations fiables, d\'etecter les anomalies, faciliter la validation de l'ex\'ecution merchandising et fournir aux superviseurs des indicateurs exploitables ?}

\section{Objectifs du projet}
Les objectifs du projet sont :
\begin{itemize}
    \item construire une base de donn\'ees MySQL \`a partir des fichiers Excel extraits du portail ;
    \item transformer, nettoyer et charger les donn\'ees afin de les rendre exploitables ;
    \item d\'efinir des r\`egles de validation pour identifier les anomalies dans les donn\'ees magasins ;
    \item d\'evelopper une plateforme web permettant de consulter, contr\^oler et valider les donn\'ees d'ex\'ecution ;
    \item pr\'eparer une application mobile destin\'ee aux superviseurs pour remplacer progressivement le rapport quotidien manuel ;
    \item construire des tableaux de bord Power BI pour analyser la performance merchandising ;
    \item documenter l'\'evolution du projet en parall\`ele avec son d\'eveloppement.
\end{itemize}

\section{M\'ethodologie de r\'ealisation}
La r\'ealisation du projet suit une d\'emarche progressive orient\'ee donn\'ees. La premi\`ere \'etape consiste \`a comprendre la structure des fichiers Excel extraits du portail et \`a identifier les cl\'es m\'etier principales, notamment le code magasin, le code merchandiser et la date de visite.

La deuxi\`eme \'etape concerne la conception et l'alimentation de la base de donn\'ees MySQL. Les donn\'ees brutes sont transform\'ees, nettoy\'ees et organis\'ees dans des tables permettant l'analyse et le contr\^ole de l'ex\'ecution merchandising.

La troisi\`eme \'etape porte sur la mise en place des r\`egles de validation. Ces r\`egles permettent de d\'etecter les anomalies, telles que les incoh\'erences de disponibilit\'e produit, les probl\`emes GPS, les doublons ou les donn\'ees manquantes.

Enfin, les donn\'ees valid\'ees sont expos\'ees \`a travers une API backend, une plateforme web de suivi, une application mobile destin\'ee aux superviseurs et des tableaux de bord Power BI. Cette d\'emarche permet de construire le projet en parall\`ele avec la documentation du rapport.

\section{Data engineering et Business Intelligence}
Le volet data engineering constitue la base du projet. Son r\^ole est de transformer les fichiers Excel extraits du portail en donn\'ees structur\'ees, fiables et exploitables par la base MySQL, le backend, la plateforme web, l'application mobile et les tableaux de bord Power BI.

\subsection{Principe du pipeline ETL}
Le pipeline suit une logique ETL : extraction, transformation et chargement. L'extraction consiste \`a r\'ecup\'erer un fichier Excel local ou \`a le t\'el\'echarger automatiquement depuis le portail. La transformation permet de nettoyer les colonnes, convertir les dates, construire les entit\'es principales et pr\'eparer les r\'eponses terrain. Le chargement ins\`ere ensuite les donn\'ees dans la base MySQL.

Le point d'entr\'ee principal du pipeline est le script \texttt{data-engineering/main.py}. Ce script permet de choisir la source de donn\'ees, d'appliquer un filtre de date, de lancer le chargement principal, de construire la table analytique \texttt{survey\_responses} et d'ex\'ecuter les r\`egles de validation lorsque le chargement correspond \`a un traitement quotidien.

\subsection{Transformation des donn\'ees sources}
Le fichier Excel brut contient plusieurs types d'informations : merchandisers, magasins, produits, visites, t\^aches, questions, r\'eponses et coordonn\'ees GPS. La premi\`ere transformation consiste \`a normaliser les noms de colonnes, convertir la colonne \texttt{dateid} en date r\'eelle et convertir \texttt{responseDate} en date exploitable.

Le pipeline construit ensuite quatre tables de base :
\begin{itemize}
    \item \texttt{employees}, identifi\'ee par le code merchandiser ;
    \item \texttt{stores}, identifi\'ee par le code magasin ;
    \item \texttt{products}, identifi\'ee par le code produit ;
    \item \texttt{visits}, d\'efinie par la combinaison d'une date, d'un merchandiser et d'un magasin.
\end{itemize}

Cette mod\'elisation est importante, car le fichier Excel contient plusieurs lignes pour une m\^eme visite. Chaque ligne peut repr\'esenter une question, une r\'eponse, un produit ou une t\^ache diff\'erente.

\subsection{Tables dynamiques de t\^aches}
Certaines t\^aches du fichier Excel sont transform\'ees en tables dynamiques. Par exemple, les t\^aches \texttt{LOCATION CHECK IN}, \texttt{LOCATION CHECK OUT}, \texttt{CALLCYCLE DEVIATION}, \texttt{OSA}, \texttt{SOS} ou encore \texttt{PRICE} sont orient\'ees vers des tables sp\'ecifiques de type \texttt{task\_*}.

Cette approche permet d'adapter automatiquement la base aux diff\'erentes questions pr\'esentes dans les fichiers du portail. Les questions peuvent devenir des colonnes dans les tables de t\^aches, ce qui facilite certains contr\^oles m\'etier et certaines analyses.

\subsection{Table analytique normalis\'ee}
En plus des tables dynamiques, le pipeline construit une table normalis\'ee appel\'ee \texttt{survey\_responses}. Cette table conserve les r\'eponses sous une forme simple : visite, merchandiser, magasin, produit, t\^ache, question, r\'eponse, date de r\'eponse et coordonn\'ees GPS.

Cette table joue un r\^ole central pour l'analyse, car elle permet d'interroger les donn\'ees de mani\`ere flexible. Elle est utilis\'ee par les r\`egles de validation, les API backend, les tableaux de bord et les analyses Power BI.

\subsection{Validation apr\`es chargement}
Apr\`es un chargement quotidien, le pipeline peut ex\'ecuter automatiquement des r\`egles de validation. Les r\'esultats sont enregistr\'es dans les tables \texttt{validation\_rules}, \texttt{validation\_run\_log} et \texttt{validation\_results}.

Deux r\`egles sont actuellement pr\'esentes dans le projet. La premi\`ere identifie les r\'eponses OSA suspectes lorsqu'un produit est marqu\'e \textit{Non} alors que le m\^eme produit pr\'esente une forte tendance de disponibilit\'e \textit{Oui} pour la m\^eme enseigne. La deuxi\`eme d\'etecte les positions GPS incoh\'erentes lorsque les visites r\'ep\'et\'ees d'un m\^eme magasin par un m\^eme merchandiser s'\'eloignent fortement de la zone GPS habituelle.

La couche Business Intelligence sera construite \`a partir de ces donn\'ees structur\'ees afin de produire des indicateurs sur l'ex\'ecution terrain, la couverture magasins, les anomalies et la disponibilit\'e produit.
